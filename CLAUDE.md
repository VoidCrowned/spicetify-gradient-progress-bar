# CLAUDE.md — Gradient Progress Bar

A Spicetify extension that recolours Spotify's **song progress bar** with one solid colour or a multi-stop gradient. It must coexist cleanly with themes and other extensions, because it's published to the Spicetify Marketplace — not just used on the author's setup.

Everything under *Verified facts* was confirmed from the live DOM (Spotify 1.3.3.264; rendering re-verified on **1.3.4.258** by the self-test, #25) and from the source of the theme and extension it runs alongside. Don't re-derive it and don't "improve" on it by guessing. If something depends on the live Spotify DOM and can't be known from this repo, **give the maintainer a devtools console snippet to verify it** instead of assuming.

## Verified facts — Spotify DOM

Song progress bar structure:

```
[data-testid="playback-progressbar"]          ← wrapper, hashed class; STABLE scope hook
└─ .progress-bar  [data-testid="progress-bar"] ← owns the CSS variables
   └─ .x-progressBar-progressBarBg [data-testid="progress-bar-background"]
      ├─ .x-progressBar-sliderArea             ← track (no fill inside)
      ├─ .x-progressBar-sliderArea             ← contains the fill
      │  └─ .x-progressBar-fillColor           ← THE FILL
      └─ [data-testid="progress-bar-handle"]   ← the knob (hashed class)
```

1.3.4.258 adds a visually-hidden `label > input` (range input, accessibility) before `.progress-bar`, and an extra hashed `div` as the first child of `.x-progressBar-progressBarBg`. Neither affects our selectors.

Spotify's own rules (relevant parts):

```css
.progress-bar {
  --bg-color: rgba(var(--spice-rgb-text), .30);
  --fg-color: var(--spice-text);
  --is-active-fg-color: var(--spice-button);
  --progress-bar-transform: 0%;   /* live playback position, e.g. "94.06%" */
  --progress-bar-height: 4px;
  --progress-bar-radius: calc(var(--progress-bar-height) / 2);
}
.x-progressBar-fillColor {
  background-color: var(--fg-color);
  width: 100%;
  transform: translateX(calc(0% - (100% - var(--progress-bar-transform))));
}
[handle] { background-color: var(--fg-color, var(--spice-text)); left: var(--progress-bar-transform); }
```

- The fill is a **full-width element translated left**; its visible part is the rightmost `--progress-bar-transform` percent.
- **The volume slider is the identical component** (same classes, same wrapper class) but without the `playback-progressbar` test id. Every rule must be scoped so it never affects the volume bar.

## Verified facts — coexistence

### Hazy theme ([Astromations/Hazy](https://github.com/Astromations/Hazy)) — #11

- Touches the bar only via variables, single-class selectors, no `!important`:
  `.progress-bar { --bg-color: rgba(255, 555, 255, 0.2); --fg-color: var(--spice-button); --is-active-fg-color: var(--spice-button-active); }` plus a box-shadow on `.x-progressBar-sliderArea`. (`555` is a typo; Chromium clamps it.)
- `--spice-button` is set **at runtime** as an inline style on `:root` by `hazy.js` on every `songchange`: with *Custom color* on, the user's fixed colour; otherwise the most frequent pixel colour (very dark and near-white pixels skipped) of Hazy's background image, which is the album art, or the user's picture when *Custom background* is on (then constant across songs). There is no Spotify-green fallback. Verified with the maintainer, 17 Oct (#38). Never read theme colours from a theme's `color.ini` — only the live computed value, or better, `var(--spice-button)` in CSS.
- `--spice-rgb-button` is stale under Hazy: it keeps the colour scheme's value while `--spice-button` changes. Tint with `color-mix(in srgb, var(--spice-button) 30%, transparent)`, never `rgba(var(--spice-rgb-button), …)` (#40). The other `--spice-rgb-*` variables are fine; Hazy doesn't change them at runtime.
- Hazy calls `document.getElementById("color-input")` and styles generic classes globally (`.slider`, `.toggle`, `.toggleWrapper`, `select`). Never use those ids/classes.

### playback-bar-waveform ([Konsl/spicetify-extensions](https://github.com/Konsl/spicetify-extensions)) — #12

Turns the bar into a 24 px audio waveform using **Web Animations API held animations** (`element.animate([...], { fill: "forwards" })`). These beat all normal CSS and are invisible to stylesheet/`style`-attribute inspection — find them with `element.getAnimations()`.

| Element | Change | How |
|---|---|---|
| `.playback-bar` | height → 24 px | animation |
| `.progress-bar` | `--progress-bar-height: 24px`, `--progress-bar-radius: 0px` (registered via `CSS.registerProperty`) | animation |
| `.x-progressBar-progressBarBg` | `background: none` | `<style>` |
| sliderArea **without** the fill | `background: var(--bg-color)` | `<style>` |
| **both** sliderAreas | `mask: url(#progress_bar_waveform_mask)` | animation |
| handle | 2 px × 24 px line, no shadow, hover timestamp tooltip | animation + `<style>` |

It never touches the fill's background, so our gradient is cut into the waveform shape by the parent's mask — this is desired. Its selector constants are a good reference list of historical Spotify class names.

### Spicetify PopupModal

`Spicetify.PopupModal` is a custom element (`generic-modal`, `_HTMLGenericModal` in spicetifyWrapper). `display()` rebuilds its innerHTML, appends our content into its `<main>` and appends itself to `<body>`; `hide()` removes it. Its **overlay click handler hides the modal when `.GenericModal` doesn't `contains(event.target)`** — so a click whose target we detach during dispatch (e.g. re-rendering the stop that owns the clicked ✕) closes the modal. **Never remove or replace the clicked element synchronously in a click handler; defer with `setTimeout(…, 0)`** (#26).

Themes may give the dialog `backdrop-filter` or `transform` (Hazy blurs it). Either makes the dialog the **containing block for `position: fixed`** descendants, so a fixed popover is positioned and clipped by the dialog. **No large popovers inside the modal** — only small ones that fit (the dot menu); anything bigger goes inline (#35). The self-test hit-tests every control with `elementFromPoint` after `scrollIntoView` to catch clipping.

**Bottom spacing (#48).** The popup markup (Spicetify 2.45.3) is `.GenericModal.spicetify-popup` › `.spicetify-popup-container.main-trackCreditsModal-container` › header + `.spicetify-popup-content.main-trackCreditsModal-mainSection` (`padding: 0 24px 24px`, scrolls) › `<main class="main-trackCreditsModal-originalCredits">` › our root. Spotify's own CSS has no rules for those readable `main-trackCreditsModal-*` names, but themes target them: **Hazy's `app.css` gives `.main-trackCreditsModal-container` `padding-bottom: 32px`**, so the space below the help text was 24 + 32 = 56 px against 24 px at the sides (measured in Chromium with Spicetify's popup markup and CSS plus Hazy's rules; the help paragraph and `<main>` add 0). `evenPopupBottom()` in `openModal()` sets inline `padding-bottom: 0` on the container and the content's `padding-bottom` to its own `padding-left`. That's safe because `display()` rebuilds the markup each time, so the next popup (any extension's) starts clean; the self-test checks it. **Never a global rule** for Spicetify's popup classes.

## Hard rules

1. **Scope everything** with `SCOPE` (below). The volume bar must never change.
2. **Never set** `mask`, `height`, `width`, `transform`, `--progress-bar-height`, `--progress-bar-radius`, `--progress-bar-transform`, or any layout property on bar elements. **One exception (#15):** in Anchored mode, the fill rule (`${SCOPE} ${FILL}`) sets `transform: none` and `clip-path: inset(…)` — nowhere else, in no other mode. `cssProblems(css, mode)` in the self-test enforces exactly that.
3. **Don't override** `--fg-color`, `--bg-color`, `--is-active-fg-color` — themes and extensions read them.
4. **No `!important`.** Win by specificity: attribute + class ≥ 0,2,0 beats Hazy's 0,1,0. `!important` would also break the waveform's held animations.
5. **No element references from JS** for the bar. Pure CSS selectors survive React re-renders, other extensions' re-query cycles and Spotify updates.
6. **Inert by default**: with default settings the stylesheet is empty.
7. Never hard-code bar geometry; `--progress-bar-radius` is `2px` normally and `0px` under the waveform.

## Rendering — #1, #6

One `<style id="gpb-style">` in `<head>`, fully regenerated whenever settings change.

```js
const SCOPE  = ':is([data-testid="playback-progressbar"], .main-nowPlayingBar-center .playback-bar)';
const FILL   = '.x-progressBar-fillColor';
const HANDLE = ':is([data-testid="progress-bar-handle"], .progress-bar__slider, .x-progressBar-handle)';
```

**Gradient on** — `settings.mode` ("Spread", #15) picks the declarations after `background-image`; the handle is the last stop in every mode.

**Compress** (the default: full gradient always spans bar start → playhead):

```css
${SCOPE} ${FILL} {
  background-image: linear-gradient(90deg, <stops>);
  background-size: var(--progress-bar-transform) 100%;
  background-position: right center;
  background-repeat: no-repeat;
}
${SCOPE} ${HANDLE} { background-color: <last stop>; }
```

**Solid:**

```css
${SCOPE} ${FILL}   { background-image: linear-gradient(<c>, <c>); }
${SCOPE} ${HANDLE} { background-color: <c>; }
```

Solid also uses `background-image` so Spotify's hover swap of `background-color` stays hidden underneath. Stops are evenly spaced. A **theme stop** is emitted as `var(--spice-button, var(--spice-text, #1db954))`, never a resolved hex (#7).

**Solid with a theme first stop is inert** (empty stylesheet), whether or not unused stops follow — the bar keeps the theme's own colour (`--fg-color`). Decided with the maintainer; it keeps the default state empty (#1).

**Anchored** (gradient fixed to the track, revealed as the song plays; undoes Spotify's translate and clips at the playhead instead):

```css
${SCOPE} ${FILL} {
  background-image: linear-gradient(90deg, <stops>);
  background-size: 100% 100%;
  transform: none;
  clip-path: inset(0 calc(100% - var(--progress-bar-transform)) 0 0 round var(--progress-bar-radius));
}
```

It composes with playback-bar-waveform: the waveform's mask is on the parent slider area, our clip-path on the fill. In Anchored the handle colour differs from the colour under the playhead until #22.

**Slide** (the full-track gradient slides in with the fill; only its tail shows early on): `background-image` only, no size, position, transform or clip-path.

Solid output is byte-identical in all three modes; default settings stay inert in every mode.

## Data model — #2

`Spicetify.LocalStorage`, key `gpb:settings`:

```json
{ "version": 1, "gradient": false, "mode": "compress", "stops": [ { "id": "s1", "kind": "theme" } ] }
```

`mode` (#15) is `"compress" | "anchored" | "slide"`, optional and additive (schema `version` stays 1): missing → `"compress"` silently (settings saved before v1.2.0), any other value is invalid. Kept while the gradient is off; Reset → `"compress"`. `kind: "theme"` has no `color`; `kind: "custom"` has `"color": "#rrggbb"`. 1–8 stops. Invalid → defaults + one `[gpb]` warning. Apply CSS on every input event; persist debounced (~250 ms).

## UI behaviour — #3–#5, #7–#10

- Entry: **right-click the song progress bar** (always), plus a profile-menu entry **and** a top-bar button, both at the same time, wherever Spicetify can render them (#28, #45).
- Gradient switch off by default; **adding a 2nd stop turns it on**; **removing to 1 stop turns it off**. **Never disabled (#46):** with 1 stop, switching it on does exactly what adding a colour does (`toggleGradient()` → `addStop()`: a copy of the stop, a theme stop stays theme, the new dot selected, gradient on); focus stays on the switch, which is only updated in place (`aria-checked`). Switching off keeps the stops (colours 2+ dimmed). No tooltip on the row. `addStop()` is `duplicateStop()` on the last stop, so adding, Duplicate and the switch all copy a stop the same way.
- **Dots are plain `<button>`s: left-click selects, right-click opens a menu, drag reorders** (HTML5 DnD on the dot itself; a click within 300 ms of a drag is ignored, so a drag never changes the selection). No icons on the dots, no dashed ring. Tooltip: the colour ("Theme colour" for theme dots), plus a second line "Drag or Alt+←/→ to reorder" with 2+ stops. `aria-label` is position-aware: "Colour 2 of 3: #ff0000".
- **−|+ stepper (#49, replaces the round + of #47)** — one pill `.gpb-stepper` (`role="group"`, `aria-label="Colours"`) directly after the last dot: the height of a dot (32 px) and 71 px wide; the pill has no border of its own and there's no divider element (#50). **Each half draws its own "D"**: every `.gpb-step` is a 36 × 32 px border box (34 px between its borders) with a 1 px border `rgba(var(--spice-rgb-text), .3)`; **−** has `border-radius: 16px 0 0 16px` and its right edge is the middle line; **+** has `border-radius: 0 16px 16px 0`, `margin-left: -1px` and a **transparent left border** at rest, so the middle is one line at the normal colour (two overlapping translucent borders would look brighter). **Hover, like Reset's border (#50):** `.gpb-step:hover:not(:disabled)` sets `border-color` and `color` to `var(--spice-text)`, so the hovered D's whole outline (middle line included) and its icon brighten; `.gpb-plus:hover:not(:disabled)` adds `position: relative; z-index: 1`, so +'s now visible left border sits over −'s right edge. The icons are `--spice-subtext` at rest (under Hazy that's barely different from `--spice-text`, hence the outline). Disabled halves get no hover and dim only the icon, so the outline stays even; focus ring inset (`outline-offset: -3px`). The self-test reads the hover rules through CSSOM, since real `:hover` can't be triggered from script. **−**: `aria-label`/`title` "Remove selected colour", calls `removeStop(selectedId)` — exactly the dot menu's Remove, so the selection rule (#35) and "down to one colour turns the gradient off" apply; disabled at 1 colour with `title` "At least one colour". **+**: "Add colour", `addStop()`, disabled at 8 with "Up to 8 colours". Focus stays on the clicked half; if that half is now disabled, focus moves to the selected dot. The pill lives **outside** `.gpb-stops`, in the `.gpb-dots` flex line with it, because `renderStops()` empties `.gpb-stops` and a clicked node must never be detached (#26); `.gpb-dots`' 10 px gap plus `.gpb-stops`' 4 px padding puts it `STOP_GAP` (14 px) after the last dot. Not a dot: not draggable, and the drag-and-drop, Alt+arrow, Delete and dot-menu listeners (all on `.gpb-stops`) never see it. Tab order: dots, −, +.
- **Keyboard reordering (#24)** — on a focused dot, Alt+←/→ moves it one place, Alt+Home/End to the first/last place, via `moveStop()`; nothing at the edges (the key is still consumed: Alt+←/→ is Spotify's Back/Forward). Focus goes to the re-rendered dot with the same `data-id`, the selection is unchanged, and the visually hidden `.gpb-announce` (`aria-live="polite"`, after the menu markup) says "Moved to position N of M". Plain arrows, Enter/Space and Shift+F10 are untouched. **Delete and Backspace (#49)** on a focused dot (no modifier keys) remove *that* dot — not necessarily the selected one — through `removeStop()` (`enableKeyboardRemove()`, also on `.gpb-stops`, so the hex and R/G/B fields keep Backspace); focus goes to the dot now at that index (clamped) and `.gpb-announce` says "Colour removed, N left". At 1 colour nothing is removed, but the key is still consumed (`preventDefault` and `stopPropagation` either way).
- **Selection (#35)** — exactly one dot is selected and has the ring. The first on open and after Reset; Add and Duplicate select the new dot; removing the selected dot (Remove, −, or Delete/Backspace on it) selects the one now at its index (clamped); removing another keeps it; right-click doesn't change it. Clicking a dot only selects it (ring moved in place, the row isn't re-rendered); Enter/Space on a focused dot selects it and moves focus to the hex field.
- **Colour picker (#32, #35)** — our own, because Chromium's native popup is browser chrome and can't be extended. An **inline panel** between the dots and the action row that always shows the selected stop — not a popover (see *Spicetify PopupModal*). Two columns from 420 px of content (flex-wrap, 202 + 16 + 202 px), stacked below: left the saturation/value square; right the eyedropper (only if `window.EyeDropper` exists), swatch and hue bar, then R/G/B fields, the **hex row** (label `HEX:` and a fixed `10ch` monospace field, about half the column, centred together in the column in both layouts, #36; accepts `#rrggbb`/`rrggbb`/`#rgb`/`rgb`, live, invalid flagged and ignored, normalised on blur) and **Use theme colour** (disabled as *Following theme colour* on a theme stop). Drags use pointer capture, coalesced per animation frame. Editing a theme stop turns it custom. Picker edits update the dot in place and never re-render the dots row.
- **Dot menu (#33)** — a popover at the cursor: **Duplicate** (copy directly after; a theme stop stays theme; disabled at 8; 1 → 2 turns gradient on) and **Remove** (disabled with 1; down to 1 turns gradient off). Context-menu key / Shift+F10 opens it under the dot; arrows, Home/End, Enter; Tab or Escape close it (focus back on the dot); a click or focus elsewhere closes it.
- **Popover rules** (the menu is the only popover): rendered **inside the modal root** (`position: fixed`, offset-corrected if an ancestor is transformed) — never in `<body>` (#26). **Hidden, never removed**, so a clicked element is never detached during its own click. Menu actions hide it first, then act. Anything that re-renders the dots row (`renderModal`) closes it first.
- **Spread row (#15)** — directly under the Gradient row: label *Spread*, a `role="radiogroup"` of three `role="radio"` buttons *Compress · Anchored · Slide* (`aria-checked`, roving tabindex; ←/→ wrap, Home/End, without modifier keys), and a one-line hint for the active mode (*Applies when the gradient is on.* while it's off, when the buttons are disabled). **No `<select>`** (Hazy styles `select` globally). **The checked button is filled** with `var(--spice-button)` at full strength (border transparent, so the size doesn't change; disabled keeps the fill at the usual 50 % opacity). **Its label takes whichever of `--spice-text` and `--spice-main` has the higher WCAG contrast** against the *computed* `--spice-button` (class `gpb-on-light` → `--spice-main`, #43); computed colours are read through `color-mix(in srgb, …)` so they always come back as `rgb()`/`color(srgb …)`. Built once per open and only updated in place by `renderSpread()` (`aria-checked`, `tabIndex`, `disabled`, `gpb-on-light`, hint) — `renderModal()` never replaces it (#26). `watchThemeColour()` (the `:root` style observer and `songchange`, open modal only) calls `renderSpread()` too, so the label follows a runtime theme colour. A mode click calls `setMode()` → `update({ rerender: false })`. The preview keeps showing the full gradient in every mode.
- **Layout (#37)**, top to bottom: Gradient row → Spread row → preview → dots and the −|+ stepper (`.gpb-dots`) → picker → **action row** (only *Reset*, horizontally centred, #47) → **help text last**, two lines (`<br>`): "Click a colour to edit it, drag to reorder, right-click to duplicate. + adds a colour, − removes the selected one." (#49) / "Reset goes back to a single colour that follows your theme." No footer; the space below the help text matches the sides (self-test: within 4 px, measured to the dialog's edges, #48). The menu popover's markup sits first in the root (hidden, fixed), so the help text is the root's last child. Spacing (#34): `padding-top: 20px` on the modal root under Spicetify's title bar, and the help text 28 px below the action row; the self-test requires both gaps ≥ 16 px. Max 8 stops; preview strip.
- **Reset is two-step (#37), no dialog**: the first click (or Enter/Space) only arms it — label *Confirm reset?*, text and border `var(--spice-notification-error, #e91429)` (class `gpb-armed`) — for `RESET_CONFIRM_MS` = 3 s; a second click resets (defaults, first dot selected, label back to *Reset*). It disarms without resetting after 3 s, on Escape (stopped there, so the modal stays), on blur, or on any other pointerdown, click or keydown in the window. Only the label span's text and the class change, never the button node (#26). The label span is `aria-live="polite"`; a hidden copy of *Confirm reset?* in the same grid cell keeps the width fixed. The timer is cleared on close, so reopening shows *Reset*.
- Theme swatches kept live while the modal is open (MutationObserver on `:root` `style` + `songchange`), disconnected on close.
- Modal colours only from Spicetify variables.

## Lifecycle

- `window.__gpb = { version, status, selfTest }` is defined on the **first line**, before any waiting, so a stuck or failed start-up is visible via `__gpb.status()`.
- Wait only for what's required: `LocalStorage`, `PopupModal`, `Player` (warn after 10 s which ones are missing). Use `window.Spicetify?.x`, never bare `Spicetify?.x` (throws if the global doesn't exist).
- Apply the stylesheet **before** registering the entry point: the bar must work even if no menu can be added.
- Entry points: **right-click on the song progress bar always opens the settings** (one delegated `contextmenu` listener on `document`, capture phase, `closest(SCOPE)`; no Spicetify UI wrapper involved) and `__gpb.open()`. `Spicetify.Menu.Item` and `Spicetify.Topbar.Button` are **both** registered, independently and in parallel (`registerSpicetifyEntries()` → `registerMenuEntry()` + `registerTopbarEntry()`, #45): people look for settings in different places, so neither is the other's fallback, and the menu's `ReactJSX` wait never delays the top bar. One top-bar button at most, kept on `window.__gpb.topbarButton`; it counts in `startup.entry` only once its element is connected, but one that isn't on screen yet stays registered, because Spicetify mounts it once it finds its top bar. `status()` has `topbar: { created, connected }`. Both use `ENTRY_ICON` (#44), a brush over a progress bar: monochrome (`currentColor`), 16 × 16, no `<defs>`, no `id`s. The top bar sets it as the button's innerHTML; `Menu.Item`'s 4th argument (`leadingIcon`) goes through Spicetify's `createIconComponent()`, which nests it inside Spotify's `IconComponent` — the same way Spicetify renders its own named icons. **On Spotify 1.3.4.258 / Spicetify 2.45.3**: Topbar buttons silently never render (Hazy's pencil is gone too, #28). Root cause (#38): Spicetify's `topbar.js` waits for `.main-globalNav-historyButtons`, a readable class that `spicetify apply` adds from `css-map.json`, and the map lacked Spotify 1.3.4's new hash. Fixed upstream in spicetify/cli@1684023 (11 Oct) but not released as of v2.45.3, so the top bar comes back with the next Spicetify release. Temporary workaround for testing, in the devtools console (lasts until reload): `document.querySelector(".main-globalNav-historyButtonsWrapper [data-encore-id='buttonTertiary']")?.parentElement.classList.add("main-globalNav-historyButtons")`. **Never put that workaround into the extension**: it changes Spotify's DOM for every other extension and theme, and the upstream fix makes it unnecessary. **Profile menu (#27, verified 16 Oct on Spotify 1.3.4.258 / Spicetify 2.45.3 and in spicetify/cli main de53c42):** `Spicetify.Menu.Item` extends `ContextMenuV2.Item`, whose constructor calls `Spicetify.ReactJSX.jsx(…)` immediately; `ReactJSX` is only set later by spicetify-bindings. CLI extensions start before that and Marketplace installs after it — that was the old "reading 'jsx'". So `registerSpicetifyEntry()` first waits for `window.Spicetify?.ReactJSX?.jsx` (every 250 ms, max 15 s; on timeout the error goes to `entryErrors` and the Topbar attempt follows). Separately, `Spicetify.ReactComponent.MenuItem` resolves to Spotify's **V2-only** menu item on 1.3.4; Spicetify renders profile-menu items inside the legacy menu, so with any Spicetify item registered, clicking the profile icon throws "cannot be rendered outside a collection" and the menu doesn't open (spicetify/cli#4012). Items read `MenuItem` and their `shouldAdd` at render time. **Guard:** before `register()`, the item's `shouldAdd` is wrapped with `menuItemUsable()`, which is false only when the source of `Spicetify.ReactComponent.MenuItem` contains `forceV2LeadingIcon` but not `aria-describedby` (Spotify's layout-switching item, the correct one, has both); cached per component. On an affected build our entry is hidden rather than breaking the profile menu, and it appears by itself once `MenuItem` is fixed, without a reload. With `MenuItem` swapped to the switching item by hand, the entry renders correctly with `ENTRY_ICON`, aligned with Spicetify's own icon entries (verified 16 Oct). The item is kept on `window.__gpb.menuItem`; `status()` has `apis.ReactJSX` and `menu: { registered, menuItemUsable }`. **Never put a `MenuItem` swap or any other global Spicetify fix into this extension** — same rule as the Topbar workaround. Never depend on the menu or the top bar alone.
- Wrap start-up in `try/catch`; on failure set `status().phase = "failed"` with the stack and `console.error` it.
- The self-test's environment block has `source` (`document.currentScript.src`, captured before the first `await`) and `copies` (every `<script>` loading `gradientProgressBar.js`); one check requires exactly one copy (#39).
- `status()` and the self-test report include a DOM probe with an outline of the song bar, so selector breakage after a Spotify update can be fixed from one pasted report.
- No DOM polling for the bar.

## Testing

Two layers:

1. **Self-test (#23)** — `await __gpb.selfTest()` in devtools. Drives the extension programmatically, checks computed styles on the live DOM, restores the user's settings afterwards, prints a pass/fail table and copies a JSON report to the clipboard. Everything checkable by code lives here.
2. **Visual checklist** (`TESTING.md`; ticked per release in the test-pass issue, #14 for v1.0.0) — only what a human has to see or feel: flicker while seeking/hovering, drag-and-drop feel, colour picker opening, how it looks under the waveform and with Hazy. Keep it to ≤ 8 items.

`TESTING.md` documents both (devtools console, coverage list, checklist); keep it in sync with the self-test. Add a self-test check (preferred) or a visual item whenever a fix addresses something neither covered.
